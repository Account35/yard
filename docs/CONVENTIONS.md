# Yard conventions

Every phase follows this file. Yard is rent and tenant management for backyard-room
landlords in South Africa: a standalone, mobile-first, installable web app that works
alongside WhatsApp through `https://wa.me/<number>?text=<message>` links with pre-written
text. No WhatsApp Business API, no chatbot. Landlords sign in with phone number and SMS
code. Tenants never sign in; they open a private link at `/t/<token>`.

## Stack

TanStack Start (React 19, Vite, TypeScript strict with `noUncheckedIndexedAccess`),
TanStack Router (file-based), TanStack Query, Tailwind CSS v4, Zod, Supabase JS,
vite-plugin-pwa, Vitest. Built as a client-rendered app with a prerendered shell
(`spa` mode), deployed to Netlify as static files.

Differences from the original Phase 0 brief, required by the framework:

- Route definitions live in `src/routes/` (one file per route) instead of
  `src/router/index.tsx`. Route files stay thin: they set `head()` and lazy-load a page
  from `src/pages/` with `lazyRouteComponent`.
- There is no `main.tsx`, `App.tsx` or `index.html`. The html shell, head tags, viewport,
  theme colour and Apple touch icon live in `src/routes/__root.tsx`.
- Tailwind v4 is configured in `src/styles/index.css`. There is no `tailwind.config.ts`
  or `postcss.config.js`.

## Naming

- Components: PascalCase file names (`StatusTag.tsx`), one exported component per file.
- Hooks: `useX`.
- Database tables and columns: `snake_case`.
- Each feature owns `api.ts` (all Supabase calls), `hooks.ts` (TanStack Query hooks)
  and `schema.ts` (Zod schemas). Pages and components never call Supabase directly.
- All query keys are defined centrally in `src/lib/queryKeys.ts`.
- All route paths are defined in `src/router/paths.ts`.

## Database rules

- Migration files: four-digit number and short name, for example `0001_core_tables.sql`.
- Never edit an old migration. Every change is a new numbered file.
- Additive only: new tables, new nullable columns or columns with a safe default.
  Never drop, rename or retype an existing table or column.
- Use `CREATE TABLE IF NOT EXISTS`, `ADD COLUMN IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`.
- Every new table has Row Level Security enabled with policies so a landlord only sees
  their own data.
- After each migration, regenerate the TypeScript types (`npm run types:gen`).
- Never use or mention a service-role key in frontend code.

## Code rules

- TypeScript strict mode, no `any` (lint error).
- Money is always integer cents (ZAR). Parse with `toCents`, display with `formatMoney`.
- Dates are `YYYY-MM-DD` strings, periods are `YYYY-MM`. "Today" is `todayInSA()`.
- Phone numbers go through `parseSAPhone`: E.164 for sign-in, WhatsApp form for wa.me.
- Mobile first, tested at 360px width, fast on slow 3G. Heavy libraries (PDF) are
  lazy-loaded.
- Do not rewrite or restructure working code from earlier phases unless a phase
  requires it; extend it.
- Yard works alongside WhatsApp through wa.me links with pre-filled text.
  No WhatsApp Business API, no chatbot.
- The service worker never caches Supabase or auth requests (offline data comes in Phase 8).

## Design rules

- Calm, serious and trustworthy, like a good bank statement or a neat ledger.
- Not gamified: no badges, streaks, points, confetti or celebrations. No emoji in the UI.
- No gradients, glows, glassmorphism, sparkle icons, stock illustrations, pill shapes,
  heavy shadows or unstyled component-library defaults.
- Colours (tokens in `src/styles/index.css`): ground `#FAFAF7`, ink `#1A1A1A`,
  ink-muted `#6B6B6B`, line `#E3E2DC`, surface `#FFFFFF` (one card level only),
  brand `#1F5F3F` for primary actions only. Status colours (paid `#1F5F3F`,
  part `#B7791F`, late `#B23B3B`, neutral `#6B6B6B`) are only for payment status and
  always come with a text label. Text contrast is at least 4.5:1.
- Form errors use near-black text and a darker border, never the status red.
- One font (Inter, self-hosted, Latin, 400 and 600). Three sizes: `text-secondary`
  14px, `text-body` 16px (all form inputs), `text-title` 24px. Use `.money` for
  tabular figures on amounts.
- Radius: 4px (`rounded-sm`) for inputs and tags, 8px (`rounded-md`) for cards and sheets.
- No elevation: 1px borders and dividers only.
- 4px spacing scale, 16px page gutter (`px-gutter`).
- Visible 2px brand focus outline with offset. Respect reduced motion. Never disable zoom.
- Tap targets at least 44px; buttons 48px high. No red button: destructive actions use
  the secondary variant with clear wording.
- Plain human copy, no exclamation marks.

## Auth and onboarding (Phase 1)

- Landlords sign in with phone OTP (`supabase.auth.signInWithOtp` with the E.164 number).
  `AuthProvider` (mounted in `__root.tsx`) exposes `useAuth()`; `useLandlord()` loads the
  landlord row. `RequireAuth` and `RequireOnboarded` (in `features/auth/components`) wrap
  the `_landlord` layout. `/sign-in` and `/onboarding` are outside it.
- Ownership helpers: `public.owns_property(property_id)` and `public.owns_room(room_id)`
  (security definer, check `auth.uid()`). Every later table's RLS policies must reuse
  these instead of repeating joins.
- `public.complete_onboarding(p_name, p_language, p_property_name, p_address, p_rooms jsonb)`
  creates the landlord, property and rooms in one call as the signed-in user. It raises
  `Onboarding already completed` on a repeat call, which the app treats as success.
- Allowed values: `landlords.language` is `en`, `zu`, `xh` or `st` (English, isiZulu,
  isiXhosa, Sesotho; used for WhatsApp messages, app screens stay English).
  `landlords.reminder_tone` is `friendly` or `firm`.
- Rooms are never deleted (no delete policy); set `is_active = false` instead.
- The onboarding draft lives in localStorage under `yard.onboarding.draft`.

## Charges and payments (Phase 3)

- Migration `0004_charges_and_balances.sql` adds landlord-owned `charges` and `payments`,
  the `tenant_balances` view, and the `generate_rent_charges()` RPC. Migration `0003`
  remains reserved for the public tenant page and must not be reused.
- Money remains integer cents. Charge periods are `YYYY-MM`; due and paid dates are
  `YYYY-MM-DD`. Rent generation must be safe to call repeatedly and is triggered when
  the landlord area loads and after tenant changes.
- Confirmed payments reduce tenant balances. Pending-confirmation payments appear in
  statements but do not reduce balances; declined payments are excluded from balances
  and statements.
- Rent status is derived from the tenant balance: paid (zero or credit), late (positive
  overdue amount), part paid (current-period payment with an amount still owed), or not
  due. A status colour always appears with its text label.
- Statements combine charges and payments in date order with a running balance.
  Moved-out tenant statements are read-only. Charge edits update the amount and note;
  payment entry and reconciliation are out of scope for Phase 3.
- Dashboard summaries use the current South African month and include collected,
  expected, and outstanding amounts. Tenant status groups link to tenant details.
